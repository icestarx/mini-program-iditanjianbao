# 系统架构设计

## 1. 总体结构

```text
微信小游戏客户端
  ├── 场景与 UI
  ├── 本地缓存
  └── 只提交意图，不提交结果
        ↓
API 服务
  ├── 认证与会话
  ├── 固定摊位与货品配置
  ├── 砍价与购买
  ├── 鉴定与复盘
  ├── NPC 关系
  ├── 道具与订单
  └── 知识库
        ↓
PostgreSQL
  ├── 玩家与账本
  ├── 市场与库存
  ├── 鉴定与证据
  ├── NPC 关系
  ├── 知识库
  └── 支付订单
```

## 2. 核心原则

- **服务端权威**：真伪、估值、好感、库存、成交价、道具消耗和订单状态全部由服务端判定。
- **客户端只做展示**：客户端不提交真实价值、鉴定结论、好感增量或库存变化。
- **固定货架配置**：NPC、摊位和摊位货品由配置表维护；每摊固定 10 件，玩家访问时直接读取，不生成每日随机货架。
- **配置版本锁定**：已购买货品绑定 `product_config_version` 和 `evidence_version`，热更新不得改变历史结果。
- **业务日统一**：每日购买次数、任务和 NPC 限次按 Asia/Shanghai 05:00 切换。
- **幂等**：购买、出售、鉴定、道具、支付和任务奖励全部用 `request_id` 或唯一业务键防重。

## 3. 模块边界

| 模块 | 职责 | 不负责 |
| --- | --- | --- |
| 摊位服务 | 查询固定 NPC、摊位和 10 件货品配置 | 不生成随机货架 |
| 交易服务 | 砍价、购买、库存、出售 | 不直接改账本 |
| 鉴定服务 | 普通鉴定、专家报告、复盘证据 | 不改变真伪和估值 |
| NPC 服务 | 好感、信任、对话、令牌 | 不发放游戏币 |
| 知识库服务 | 真实馆藏文章、收藏、发布排期 | 不参与交易和经济 |
| 商城服务 | 道具、充值、订单、发货 | 不在客户端判价 |
| 账本服务 | C/G 流水、余额、审计 | 不承担业务规则 |

## 4. 关键流程

### 访问摊位

1. 玩家选择摊主并进入其摊位。
2. 服务端读取固定摊位配置及固定的 10 件货品。
3. 服务端附加该玩家的累计限购剩余次数和当日购买状态。
4. 达到限购的货品仍按产品配置展示，但购买入口标记为不可购买。

### 购买

1. 客户端提交固定 `stall_product_id`、出价或成交确认及 `request_id`。
2. 服务端校验摊位等级、货品累计限购、现金和仓容。
3. 服务端锁定钱包和限购计数，在事务中写入购买记录、玩家货品实例和账本。
4. 返回成交回执，不返回真伪和估值。

### 鉴定

1. 客户端提交鉴定意图。
2. 服务端校验状态、道具或现金。
3. 服务端写鉴定记录并锁定证据版本。
4. 报告 ready 后返回专家证据、复盘和结论。

### 支付

1. 服务端创建订单。
2. 客户端拉起微信支付。
3. 服务端凭官方回调或主动查单验证。
4. 验证通过后事务发放 `G`，并写唯一发货流水。
