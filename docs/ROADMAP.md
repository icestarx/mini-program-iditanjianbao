# 《我在地摊淘宝》执行路线图

## 1. 冻结文档基线

- 以 `我在地摊淘宝_V1.5_统一游戏开发策划.md` 和 `我在地摊淘宝_V1.5_120件物品与12摊位完整鉴定配置.md` 作为唯一有效需求基线。
- 旧版 V1.2—V1.4 只作为历史审查材料，不再作为业务规则来源。
- 后续新增需求必须先形成变更记录，再进入实现，不允许直接覆盖 V1.5 基线。

## 2. 技术选型

- 目标平台：微信小游戏。
- 前端建议优先评估 Cocos Creator 或微信小游戏原生 Canvas/WebGL 方案。
- 后端建议采用 Node.js + PostgreSQL 或 Go + PostgreSQL，优先选择团队最熟悉且能快速实现服务端权威逻辑的栈。
- 数据配置建议用 JSON/CSV + JSON Schema 校验，禁止手写散乱文档直接驱动运行时。

## 3. 架构、表设计与 API 设计

- 先输出系统架构图、模块边界和服务端权威原则。
- 同步规划微信小游戏、管理端、服务端和共享 API 契约的代码结构。
- 再输出数据库表设计，覆盖玩家、市场、物品、鉴定、NPC、知识库、订单和账本。
- 同步输出 REST API 设计和错误码约定。
- 最后把策划验收矩阵转成可执行测试用例清单。

## 4. 开发

- 先实现服务端权威市场与账本，再实现客户端界面。
- 先做 12—24 件货品的垂直切片，跑通“观察—判断—砍价—购买—鉴定—复盘—出售”闭环。
- 垂直切片稳定后，再配置完整 120 件货品和 12 个固定摊位。

## 5. 体验

- 用真机和微信开发者工具做可用性验收。
- 重点检查新手 10 分钟流程、页面跳转、按钮文案、加载状态和异常提示。
- 记录体验问题并回归，不在体验阶段临时改业务规则。

## 6. 端到端测试

- 自动化覆盖教程账本、市场快照、购买幂等、鉴定解锁、NPC 关系、知识库隔离和支付验单。
- 手工覆盖微信真机、支付能力、断网重连和跨端登录。
- 测试结果必须留档，不允许口头确认。

## 7. 发布到微信小游戏

- 完成小游戏资质、包体、支付、隐私、未成年人保护和内容合规检查。
- 通过微信开发者工具上传、提审、灰度验证后发布。
- 发布后持续观察经济、留存和崩溃指标，再决定是否开放完整内容量。
